# 约束解码

> **一句话定义**：在解码的每一步限制模型只能选择「符合给定语法」的 token，从而保证输出一定能被下游程序解析。

## 为什么需要它

把 LLM 接进软件系统时，输出必须是机器可读的——JSON、SQL、函数调用参数、特定枚举值。仅靠 prompt 里写「请输出 JSON」有两个问题：

- **无保证**。模型可能少一个引号、多一个逗号、或者在 JSON 前后加一段解释文字。
- **失败代价高**。解析失败通常只能重试，而重试的成本是一整次生成。

约束解码把「输出合法」从**概率事件**变成**结构保证**。

## 它是怎么工作的

### 基本机制：逐 token 掩码

1. 把语法（正则表达式或上下文无关文法）编译成一个状态机。
2. 解码时维护当前状态，查出该状态允许的 token 集合。
3. 把所有非法 token 的 logits 置为 $-\infty$，再采样。
4. 按采样结果做状态转移。

这样每一步的输出都合法，整体输出必然属于该语法。

### 核心难点：字符与 token 不对齐

语法定义在**字符**上，而模型输出的是 **token**。两者不是一一对应的：

- 同一段字符串可能有多种 token 化方式；
- 一个 token 可能跨越语法中的多个符号，甚至跨越状态边界；
- 因此「当前状态下哪些 token 合法」需要预先在词表上做一次昂贵的展开。

工程上的应对是**预处理一次、在一批请求间复用**。这一步的摊销往往比后续任何优化都重要。

### 效率优化：压缩确定性路径

状态机中常有一段**只有唯一合法后继**的路径——例如 JSON 里的常量串 `{"summary": "`。这些位置模型没有任何自由度，跑前向是纯粹的浪费。

把相邻的单一转移边**压缩成一条边**，就能在一次前向里跨过整段，一次解出多个 token。

**这与 speculative decoding 不同**：

| | 压缩确定性路径 | Speculative Decoding |
| --- | --- | --- |
| 额外 token 的来源 | **约束本身**（合法路径唯一） | 草稿模型的**预测** |
| 是否需要验证 | 不需要 | 需要 |
| 会不会白做功 | 不会 | 会（草稿被拒时） |
| 适用条件 | 输出受语法约束 | 任意输出 |

前者是「用约束消除计算」，后者是「用便宜的猜测换昂贵的验证」。两者正交，可叠加。

## 关键性质与代价

| 收益 | 代价 |
| --- | --- |
| 输出格式有结构保证，下游无需容错解析 | 语法编译与词表展开有预处理开销 |
| 确定性路径可压缩，解码更快 | 掩码会**扭曲原始概率分布**，可能影响输出质量 |
| 消除重试，端到端延迟更可预测 | 表达力受限于所用的语法类（正则 vs CFG） |

**概率扭曲**这一条值得单独记：把非法 token 置为 $-\infty$ 后重新归一化，得到的不是「模型在合法输出上的条件分布」。当模型本来强烈倾向于一个非法 token 时，强行掩码可能把它推向一个语义上很差的合法分支。

## 常见误解

- **误解**：约束解码保证输出**正确** → **实际**：它只保证输出**合法**（符合语法）。JSON 结构对了，字段内容仍可能是错的。
- **误解**：掩码不改变模型行为 → **实际**：重归一化后的分布与原始条件分布不同，存在概率扭曲。
- **误解**：约束解码一定更慢 → **实际**：预处理有成本，但确定性路径可以压缩；在 JSON 这类含大量常量串的格式上净效果通常是加速。
- **误解**：正则表达式够用 → **实际**：正则无法表达嵌套平衡结构（如任意深度的括号匹配），完整的 JSON 语法需要上下文无关文法。

## 出现在哪些论文里

- [SGLang / RadixAttention](../topics/llm-serving/2024-sglang-radixattention/README.md) —— 提出**压缩有限状态机**，把相邻的单一转移边压成一条，一次前向解出多个 token，JSON 解码吞吐提升 $1.6\times$；并指出状态机必须预处理一次并在批内复用，否则吞吐反而低 $2.4\times$。
