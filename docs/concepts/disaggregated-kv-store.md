# KVCache 池化与分层存储

> **一句话定义**：把 KV Cache 从「推理实例私有的显存中间产物」提升为「集群级的共享存储层」——用 GPU 节点上闲置的 CPU、DRAM、SSD 与 RDMA 网络承载它，使任意实例都能按块取用，缓存的复制、淘汰与放置随之成为独立的调度问题。

## 为什么需要它

单实例的 [prefix caching](prefix-caching.md) 只能在**同一台机器**内复用。一旦请求被路由到别的机器，之前算好的 KV 就等于不存在。集群规模越大，这个问题越严重：

$$\text{同一 key 在单机上的重访间隔} = \frac{R}{\lambda}$$

其中 $R$ 是实例数、$\lambda$ 是该 key 的到达速率。**扩容会让每台机器的缓存变冷**——这正是 [缓存亲和性与负载均衡的取舍](cache-affinity-vs-load-balance.md) 的出发点。

有两条应对路线：

| 路线 | 做法 | 代表 |
| --- | --- | --- |
| **把请求送到状态所在处** | 入口路由/亲和性调度，KV 留在本地 | 一致性哈希、CHWBL、周期性路由规划 |
| **把状态搬到共享层** | KV 池化成独立存储，任意实例可取 | 本页讨论的对象 |

第二条路线成立的前提是**跨机取 KV 比重算 KV 便宜**。这个前提在 RDMA 普及之后才真正站得住。

## 成本判据

对一个前缀长度为 $L$ 的请求，选择「拉取」还是「重算」的比较是：

$$\underbrace{\frac{L \cdot S_{\text{per-token}}}{B_{\text{net}}}}_{\text{跨机拉取}} \quad \text{vs} \quad \underbrace{T_{\text{prefill}}(L)}_{\text{本地重算}}$$

左边随 $L$ **线性**增长，右边因注意力的平方项随 $L$ **超线性**增长。因此**上下文越长，池化越划算**——这解释了为什么这条路线首先出现在长上下文场景。

反过来，短上下文下重算往往更便宜，此时池化只会白白引入网络往返。实践中通常配一条阈值规则：**当远端可复用前缀不足本地可复用前缀的某个倍数时，直接本地重算**。

## 关键设计点

### 1. 分块与哈希去重

KV 按 token 分页成块。每块的标识不能只由块内容决定，因为**同样的 token 在不同前缀下产生的 KV 不同**（注意力依赖全部历史）。标准做法是**链式哈希**：

$$h_i = \text{Hash}\big(h_{i-1} \,\|\, \text{tokens}_i\big)$$

这样两个请求只要前缀一致，块哈希序列的公共前缀就自动对齐，去重与匹配都变成前缀比较。这与 [SGLang](../topics/llm-serving/2024-sglang-radixattention/README.md) 的基数树是同一个想法的两种数据结构表达——链式哈希适合分布式查找，基数树适合单机上带共享结构的匹配。

### 2. 传输与计算重叠

朴素实现里 KV 的加载与写回是计算前后的串行步骤，会把整块 KV 的驻留时间拉长。**逐层（layer-wise）异步**是标准解法：

```
层 i 计算 ‖ 层 i+1 异步加载 ‖ 层 i-1 异步写回
```

它带来一个重要的**约束消除**：任意时刻显存里只需驻留少数几层的 KV，因此**调度时可以不把显存容量作为约束**，只需考虑缓存分布与主存容量。

### 3. 热点复制

访问分布极度倾斜——系统提示被几乎每个请求命中，而某份用户文档可能只被访问一次。生产数据显示**超过一半的块从未被复用，而少数块被访问数万次**。

单副本的热块会成为传输瓶颈，因此需要复制。复制决策有两种做法：

| 做法 | 特点 |
| --- | --- |
| **显式预测**（预测每块的未来使用量并据此复制） | 在负载快速变化时不可行 |
| **隐式复制**（请求被派到非最优实例时，让该实例主动拉取并本地留存） | 热块被反复拉取而自然复制开，冷块不会；无需任何预测 |

隐式复制的可取之处在于：它把「复制哪些块」这个难题**转化成了调度的副产品**。

### 4. 分层与淘汰

DRAM → SSD 的分层可以扩大容量，但要注意**SSD 的带宽是否还能满足「拉取比重算便宜」这个前提**。若不能，SSD 层的存在只是延缓了淘汰，并不产生收益。

淘汰策略上，生产 trace 的实测结论是 **LRU 优于 LFU 与长度感知策略**，原因是请求的复用有强时间邻近性（同一 session 内的连续轮次）。

## 容量该配多大

一个可以直接照做的测量方法：

1. 取一段真实 trace；
2. 用**无限容量**的模拟缓存跑一遍，得到**理论复用上界**；
3. 再扫描不同容量，看命中率曲线在哪里收敛。

第 2 步的数字往往令人清醒。生产环境报告的理论上界可以低到 **50% 左右**（即便假设容量与延迟约束都不存在），远低于开源基准上复现出来的数值。这个上界决定了整条路线的收益天花板：**缓存率 ~0% 的负载上，池化的收益接近于零。**

## 常见误区

- **把命中率当作收益**。命中一个块只有在「拉取比重算便宜」时才产生收益。远端命中一个很短的前缀，净效果可能是负的。
- **忽略网络与 KV 传输的相互竞争**。若模型并行本身就要跨节点通信（如跨节点 TP 或 SP），它会与 KV 传输抢同一条链路。这是选择跨节点并行方式时的一个真实约束。
- **用开源基准的命中率做容量规划**。公开数据集的前缀重复度通常远高于真实负载。

## 出现在哪些论文里

- [Mooncake（FAST'25）](../topics/llm-serving/2025-mooncake/README.md) —— 把 GPU 集群的 CPU/DRAM/SSD/RDMA 组成独立 KVCache 池，配合 layer-wise prefill 与隐式热点复制；开源了可用于复用分析的真实 trace，并报告理论复用上界约 50%。
- [CacheRoute（arXiv'26）](../topics/llm-serving/2026-cacheroute/README.md) —— 相反路线：不搬 KV，改为在入口做周期性路由规划让请求回到 KV 所在的实例。
- [SGLang（NeurIPS'24）](../topics/llm-serving/2024-sglang-radixattention/README.md) —— 单实例内的前缀复用，是池化方案在单机上的对应物。
