# Megatron-LM: Training Multi-Billion Parameter Language Models Using Model Parallelism

> **一句话结论**：不写编译器、不改优化器，只往 PyTorch 里插两个互为共轭的通信原语 $f$ 与 $g$——靠「第一个 GEMM 按列切、第二个按行切」这一个组合技巧，把每个 Transformer 层的通信压到**前向 2 次 + 反向 2 次 all-reduce**，在 512 张 V100 上训到 83 亿参数、维持 15.1 PetaFLOPs、达到线性扩展的 76%。

## 2. 摘要速览（5 分钟版）

### 2.1 要解决的问题

2019 年的处境：语言模型越大效果越好，但**模型必须能装进一张卡**。数据并行（把 minibatch 切开）只解决吞吐，不解决容量——每个 worker 仍要放下完整的模型。当 BERT、GPT-2 逼近加速卡的显存上限时，这条路就走到头了。

已有的绕法各有代价：

- **参数共享**（ALBERT）能省显存，但**限制了模型的总容量**；
- **激活检查点**只省激活，不省参数；
- **流水并行**（GPipe、PipeDream）：基于参数服务器的方案有一致性问题；GPipe 用同步梯度下降解决了一致性，但需要额外的流水编排逻辑，且**存在降低效率的流水气泡**，或者要改动优化器本身从而影响精度；
- **分布式张量计算**（Mesh-TensorFlow、FlexFlow）更通用，但需要**新的语言与编译器**。

论文的定位很清楚：借用 Mesh-TensorFlow 的洞见（利用注意力头的天然并行性），但**不做框架也不做编译器**——只对现有 PyTorch Transformer 实现做几处针对性修改。

### 2.2 核心方法

整套方法可以浓缩成一条原则：**让切分方式服从非线性算子的位置，从而消除本可避免的同步点**。

**MLP 块**。两层 GEMM，中间夹一个 GeLU：$Y=\mathrm{GeLU}(XA)$，再 $Z = YB$。

- 若把 $A$ **按行**切、$X$ 按列切，得到 $Y = \mathrm{GeLU}(X_1A_1 + X_2A_2)$。由于 GeLU 是非线性的，$\mathrm{GeLU}(X_1A_1+X_2A_2)\neq \mathrm{GeLU}(X_1A_1)+\mathrm{GeLU}(X_2A_2)$，**必须在 GeLU 之前插一次同步**。
- 若把 $A$ **按列**切 $A=[A_1,A_2]$，则 $[Y_1,Y_2]=[\mathrm{GeLU}(XA_1),\mathrm{GeLU}(XA_2)]$——GeLU 可以在每个分区上**独立施加**，同步点消失。

于是第一个 GEMM 按列切、第二个 GEMM **按行**切，后者直接吃下 GeLU 的输出，中间**不需要任何通信**。只在第二个 GEMM 之后做一次 all-reduce。

**自注意力块**。利用多头注意力**本身就有的并行性**：把 $Q$、$K$、$V$ 的 GEMM 按列切，使**每个注意力头的矩阵乘完全落在一张 GPU 上本地完成**，中间不需要通信。之后的输出线性层按行切，直接接收并行注意力层的输出。

**结果**：MLP 与注意力都变成「一对 GEMM 融合、中间的同步点被消除」的结构，于是一个 Transformer 层的所有 GEMM 只需**前向 2 次 all-reduce + 反向 2 次 all-reduce，共 4 次**。

**两个共轭算子**。实现只靠 $f$ 与 $g$：$f$ 前向恒等、反向 all-reduce；$g$ 前向 all-reduce、反向恒等。论文给了 $f$ 的完整实现，只有几行 PyTorch autograd。

**其余部分怎么处理**：

- **LayerNorm、dropout、残差**：**不切，直接在每张 GPU 上复制计算**。论文的理由是「与其让一张 GPU 算一部分再广播，不如各算各的」——目标是减少通信、让 GPU 保持算力受限。每张卡维护一份重复的 LayerNorm 参数。
- **embedding**：输入 embedding 矩阵 $E_{H\times v}$ 按**词表维度**切（列切），因此输入 embedding 后需要一次 all-reduce。输出 embedding 与输入共享权重，若做并行 GEMM 再 all-gather，通信量是 $b\times s\times v$（$v$ 高达五万，极其昂贵）；**论文把并行 GEMM 的输出与交叉熵损失融合**，把通信维度降到 $b\times s$——传标量损失而不是 logits。

### 2.3 主要结果

**硬件**：至多 32 台 DGX-2H（共 **512 张 Tesla V100 SXM3 32GB**）。机内 NVSwitch 提供 300 GB/s，机间 8 个 InfiniBand 适配器提供 100 GB/s。

**扩展性**（GPT-2，每个注意力头的 hidden size 固定为 96，词表 padding 到 51,200）：

| Hidden | 头数 | 层数 | 参数量 | 模型并行 GPU | 模型+数据并行 GPU |
| --- | --- | --- | --- | --- | --- |
| 1536 | 16 | 40 | 1.2B | 1 | 64 |
| 1920 | 20 | 54 | 2.5B | 2 | 128 |
| 2304 | 24 | 64 | 4.2B | 4 | 256 |
| 3072 | 32 | 72 | 8.3B | 8 | 512 |

基线是单卡 1.2B 配置，达到 **39 TeraFLOPS**（单卡理论峰值的 30%）——论文强调这是个**强基线**。

- 8.3B + 8 路模型并行（8 GPU）：达到线性扩展的 **77%**；
- 8.3B + 8 路模型并行 × 64 路数据并行（512 GPU）：达到线性扩展的 **74%**，整个应用维持 **15.1 PetaFLOPs**。

模型并行用固定 batch size 8；模型+数据并行固定全局 batch size 512。

**模型质量**（GPT-2 零样本，训练 300k 步）：

| 模型 | WikiText103 困惑度 ↓ | LAMBADA 准确率 ↑ |
| --- | --- | --- |
| 355M | 19.31 | 45.18% |
| 2.5B | 12.76 | 61.73% |
| **8.3B** | **10.81** | **66.51%** |
| 此前 SOTA | 15.79 | 63.24% |

**BERT 侧的一个独立发现**：此前工作（ALBERT）发现把 BERT 加大到 336M 以上会出现「意外的模型退化」。本文经实验证明，**重排 layer normalization 与残差连接的顺序**（即后来通称的 pre-LN）是让 BERT 式模型突破 BERT-Large 规模的**关键**——新架构消除了原架构的不稳定性且训练损失更低。论文自称「据我们所知，我们是第一个报告这个改动能训练更大 BERT 模型的」。基于此训到 3.9B，在 MNLI、QQP、SQuAD 1.1/2.0、RACE 上全面刷新 BERT 系 SOTA（RACE 测试集单模型 89.5、集成 90.9）。

**附录 D 的两组数字比正文更有信息量**：

- **注意力头数影响扩展效率**（8.3B、8 路模型并行）：16 头（每头 192）**82%** → 24 头（每头 128）80% → 32 头（每头 96）**77%**。头越多，自注意力里的 GEMM 越小、softmax 元素越多，扩展效率越低。
- **强扩展**（固定 1.2B、固定 batch size 8）：2 卡加速 **1.64×**，4 卡 2.34×，8 卡 **2.98×**。论文承认「超过 2 卡之后收益递减，因为单卡计算量下降，访存带宽与通信开销开始主导」。

### 2.4 我的评价

这篇论文的技术内核可以用两句话说完，但那两句话极其结实：**MLP 的两个 GEMM 一列切一行切，注意力按头切**。它之所以能成为此后所有大模型训练的基础设施，靠的不是复杂度，而是三个性质叠加：

1. **通信量降到了理论上很难再降的水平**（每层 4 次 all-reduce）；
2. **实现代价接近于零**——不需要编译器、不改优化器、不改模型定义，几行 PyTorch autograd；
3. **与数据并行、流水并行正交**，可以自由组合。

它同时也是一篇**典型的 2019 年 arXiv 工程报告**，而不是一篇会议论文。没有同行评审，没有与 GPipe、Mesh-TensorFlow 的实测对比（只有相关工作里的定性讨论），没有通信量的解析模型，扩展性实验的基线选择也值得推敲（见 §6.2）。把它当作「一套被证明有效的工程方案」来读是恰当的；把它当作「张量并行的完备分析」来读则会失望。

评分 ⭐⭐⭐⭐。技术贡献极其扎实且影响深远，但评测严谨度与今天的会议论文有明显差距，扣一星。

## 3. 细读

> 章节编号与原文一致（正文 6 节 + 附录 A–E）。

### 3.1 Introduction

论证从「更大的模型更好」出发，落到「但模型必须装进一张卡」这个硬约束上。论文把自己的贡献列为：一个简单高效的层内模型并行实现、无需新编译器或代码重写、在 512 张 V100 上训到 8.3B、以及 BERT 架构的 layernorm 位置发现。

> **批注**：开篇就把「不需要新编译器」当卖点摆出来，这个定位是理解全文的钥匙。同期的 Mesh-TensorFlow 在技术上更通用（能表达任意的分布式张量计算），但要求用户学一门新语言、并让图经过编译。**Megatron 赌的是「一个够用且能立刻用上的方案，胜过一个更通用但有采用门槛的方案」——事实证明它赌对了。** 这个判断在系统工作里反复出现：采用成本常常比能力上限更能决定影响力。

### 3.2 Background and Challenges

#### 2.1 Neural Language Model Pretraining / 2.2 Transformer Language Models and Multi-Head Attention

预训练语言模型的常规背景，以及 Transformer 与多头注意力的结构回顾。这两节为 §3 服务——**尤其是「多头注意力里 $h$ 个头彼此独立」这个性质**，它是注意力块切分方式的全部依据。

#### 2.3 Data and Model Parallelism in Deep Learning

这一节做了一次相当完整的方案空间梳理，值得逐层记住。

**两大范式**：

- **数据并行**：把 minibatch 切给多个 worker。按 worker 数成比例增大 minibatch（弱扩展）能得到近线性的数据吞吐扩展。**但大 batch 训练会给优化过程带来麻烦**——可能降低精度或延长收敛时间，抵消吞吐收益。后续工作（Goyal 等的 linear scaling rule、LARS、LAMB）在缓解这个问题。
- **模型并行**：把模型的显存占用与计算分布到多个 worker。

**数据并行的根本限制**（这句是全文的立论点）：

> 这些技术在能处理的问题规模上有一个**根本限制：模型必须完整地装进一个 worker**。

绕开它的办法：参数共享能省显存但**限制模型总容量**；本文选择模型并行——不仅缓解显存压力，还**独立于 microbatch 大小地增加了并行度**。

**模型并行内部又分两类**：

- **逐层的流水并行**：一组算子在一个设备上做完，输出传给流水线的下一个设备。基于参数服务器的方案（PipeDream 等）有**一致性问题**；GPipe 用同步梯度下降解决了一致性，但需要额外的流水编排逻辑，且**存在降低效率的流水气泡**，或者要改动优化器本身从而影响精度。
- **分布式张量计算**：更通用、正交的路线，把一个张量操作切到多个设备上。FlexFlow 能自动挑并行策略；Mesh-TensorFlow 提供了一门语言，由用户指定并行维度、编译器插入集合通信原语。

**本文的定位**：借用与 Mesh-TensorFlow 类似的洞见，**利用 Transformer 注意力头的并行性**，但不实现框架与编译器，只对现有 PyTorch 实现做几处针对性修改。

> **批注**：这一节把「张量并行」放回它真正的位置——它是**分布式张量计算**这一支下的一个具体实例，与流水并行是并列关系而非替代关系。论文明确说自己「与 GPipe 那类流水模型并行**正交且互补**」。今天讲 3D 并行（数据/张量/流水）时的分工，在这一节里已经完整成型了。
>
> 另外注意论文对流水并行的批评是**气泡与优化器改动**，对 Mesh-TensorFlow 的批评是**需要新语言与编译器**——两条批评都不是「做不到」，而是「代价太高」。这与它自己「几行 PyTorch」的卖点正好对仗。

### 3.3 Model Parallel Transformers

全文的技术核心，也是唯一真正提出新东西的一节。

**MLP 块的推导**。第一部分是一个 GEMM 接 GeLU：

$$Y=\mathrm{GeLU}(XA) \tag{1}$$

**方案一：$A$ 按行切、$X$ 按列切**：

$$X=[X_1, X_2],\qquad A=\begin{bmatrix}A_1\\A_2\end{bmatrix} \tag{2}$$

得到 $Y=\mathrm{GeLU}(X_1A_1+X_2A_2)$。**由于 GeLU 是非线性函数**，$\mathrm{GeLU}(X_1A_1+X_2A_2)\neq\mathrm{GeLU}(X_1A_1)+\mathrm{GeLU}(X_2A_2)$，所以**必须在 GeLU 之前设一个同步点**（先把两个部分和 all-reduce 起来才能施加 GeLU）。

**方案二：$A$ 按列切** $A=[A_1,A_2]$：

$$[Y_1,Y_2]=[\mathrm{GeLU}(XA_1),\ \mathrm{GeLU}(XA_2)] \tag{3}$$

GeLU 可以在每个分区的 GEMM 输出上**独立施加**。论文的评价是「这消除了一个同步点，因而更优」。

**于是组合方式确定了**：第一个 GEMM 按**列**并行切，第二个 GEMM 按**行**切，使它能**直接吃下 GeLU 层的输出而不需要任何通信**。第二个 GEMM 的输出在跨 GPU 归约之后再送进 dropout 层。

结果：MLP 块的两个 GEMM 都被切开，只需要**前向一次 all-reduce（$g$ 算子）、反向一次 all-reduce（$f$ 算子）**。

**两个共轭算子**。$f$ 前向恒等、反向 all-reduce；$g$ 前向 all-reduce、反向恒等。论文给出了 $f$ 的完整实现：

```python
class f(torch.autograd.Function):
    def forward(ctx, x):
        return x
    def backward(ctx, gradient):
        all_reduce(gradient)
        return gradient
# g 与 f 类似，前向 all-reduce、反向恒等
```

**自注意力块**。利用多头注意力**固有的并行性**：把 $K$、$Q$、$V$ 对应的 GEMM 按列并行切分，**使每个注意力头对应的矩阵乘在一张 GPU 上本地完成**。这样每个头的参数与计算量都被切开，且**完成自注意力不需要任何即时通信**。随后的输出线性层按行并行切分，直接接收并行注意力层的输出，同样不需要 GPU 间通信。

**汇总**：MLP 与自注意力都做到了「融合两个 GEMM、消除中间同步点」。于是一个 Transformer 层里的所有 GEMM，**前向只需 2 次 all-reduce、反向 2 次，共 4 次通信操作**。

**embedding 的特殊处理**。输出 embedding 的维度是 hidden size $H$ × 词表大小 $v$，而现代语言模型的 $v$ 达数万（GPT-2 是 50,257），所以并行化它是划算的。但输出 embedding **与输入 embedding 共享权重**，两边都要改：

- 输入 embedding 矩阵 $E_{H\times v}$ 按**词表维度**切 $E=[E_1,E_2]$（列切）。因为每个分区只有一部分 embedding 表，输入 embedding 之后需要一次 all-reduce（$g$ 算子）。
- 输出 embedding：朴素做法是并行 GEMM $[Y_1,Y_2]=[XE_1,XE_2]$ 得到 logits，再 all-gather 成 $Y$ 送进交叉熵。**但 all-gather 要通信 $b\times s\times v$ 个元素，因词表巨大而极其昂贵**。论文的做法是**把并行 GEMM 的输出与交叉熵损失融合**，把维度降到 $b\times s$——**传标量损失而不是 logits，通信量大幅下降**。

**不切的部分：复制计算**。论文把自己的方法论总结为「减少通信、让 GPU 保持算力受限」：

> 与其让一张 GPU 计算 dropout、layer normalization 或残差连接的一部分再广播给其他 GPU，我们选择**在各 GPU 上重复这些计算**。

具体做法：每张 GPU 维护一份重复的 LayerNorm 参数；模型并行区域的输出先在本地做完 dropout 与残差，再作为下一个模型并行区域的输入。优化器也让每个模型并行 worker 优化自己那份参数——**因为所有值要么是本地的、要么是各卡重复的，不需要通信更新后的参数值**。

论文的总结：方法「实现简单，只需在前向反向里加几个 all-reduce；**不需要编译器**；与 GPipe 那类流水模型并行**正交且互补**」。

> **批注**：这一节的推导值得反复读，因为它示范了一种非常干净的设计思路——**不是先定切分方案再想怎么补通信，而是先看非线性算子在哪，再倒推切分方式**。GeLU 是逐元素的，只要它的输入在每个分区上是「完整的一列」，就能本地施加；这个要求直接决定了第一个 GEMM 必须列切。第二个 GEMM 行切则是为了让它的输入分布恰好匹配上一步的输出分布。**两个约束一咬合，中间的通信就被挤没了。**
>
> 注意力那边看似是另一个技巧，其实是同一条原则：softmax 是非线性的，且它在**头内部**跨位置耦合、在**头之间**完全独立。所以沿头维度切，非线性算子的作用范围就完整地落在单卡内。**「沿着非线性算子不跨越的维度切」是这两个设计的共同判据。**
>
> 「复制计算」那段同样重要，而且容易被当作实现细节略过。它其实是一个明确的取舍：LayerNorm 相对 GEMM 的计算量微不足道，但如果切开它，就要为一个廉价算子付一次昂贵的同步。**当算子的计算成本远低于同步成本时，复制比切分便宜**——这条判据可以直接迁移。代价是每张卡都存了一份重复的 LayerNorm 参数与激活，这正是后来 **sequence parallelism** 要回收的那部分显存。

### 3.4 Setup

#### 4.1 Training Dataset

聚合了 Wikipedia、CC-Stories、RealNews、OpenWebText；BERT 训练额外加入 BooksCorpus（GPT-2 训练排除它，因为与 LAMBADA 任务重叠）。

去污染与去重做得比较认真：移除 WikiText103 测试集中出现的 Wikipedia 文章、过滤长度小于 128 token 的文档、用 **LSH 去重 Jaccard 相似度 > 0.7 的内容**。最终得到 **174 GB** 去重文本。

#### 4.2 Training Optimization and Hyperparameters

- 混合精度训练 + 动态损失缩放（利用 V100 的 Tensor Core）；
- 权重初始化 $W\sim\mathcal{N}(0, 0.02)$，**残差层之前的权重再乘 $\frac{1}{\sqrt{2N}}$**（$N$ 为层数）；
- Adam + weight decay $\lambda=0.01$，全局梯度范数裁剪 1.0，dropout 0.1；
- **每个 Transformer 层之后做激活检查点**以控制显存；
- GPT-2：序列长 1024、batch size 512、300k 步；学习率 1.5e-4，**warmup 3k 步**后单周期余弦衰减，最低降到 1e-5；
- BERT：词表 30,522，用 sentence order prediction 替代 NSP，whole word n-gram masking；batch size 1024，学习率 1.0e-4，warmup 10,000 步后线性衰减 200 万步。

> **批注**：残差前权重乘 $\frac{1}{\sqrt{2N}}$ 这一条，和 §5.3 的 pre-LN 发现是同一个问题的两个解法——**都是在压制深层堆叠时残差分支的方差累积**。论文把前者当超参数一笔带过、把后者当作独立发现大书特书，但两者其实相关。关于这条线的机制，见 [残差连接与 Layer Normalization](../../../concepts/residual-and-layer-norm.md)；warmup 的作用见 [学习率 Warmup](../../../concepts/lr-warmup.md)。

### 3.5 Experiments

**基础设施**：至多 32 台 DGX-2H，共 512 张 Tesla V100 SXM3 32GB。机内 NVSwitch **300 GB/s**，机间 8 个 InfiniBand 适配器 **100 GB/s**。

#### 5.1 Scaling Analysis / 5.1.1 Model and Data Parallelism

四组 GPT-2 配置（见 §2.3 的表）。几个实验设计细节值得记：

- **每个注意力头的 hidden size 固定为 96**，理由是让自注意力层里的 GEMM 尺寸保持一致；
- 原词表 50,257，为让 logit 层的 GEMM 高效，**每卡词表大小最好是 128 的倍数**；因为要研究到 8 路模型并行，把词表 pad 到 $128\times 8=1024$ 的倍数，得到 **51,200**；
- 模型并行扩展用固定 batch size 8；模型+数据并行固定全局 batch size 512（对应 64 路数据并行）。

**为什么用弱扩展**：论文特意说明，弱扩展通常靠增大 batch size 来做，**但那个做法既不能解决「模型装不进单卡」的问题，又会在大 batch 下导致收敛退化**。所以这里的弱扩展是**通过训练更大的模型**来实现的。

**基线**：单卡上的 1.2B 配置，达到 **39 TeraFLOPS**，是单卡理论峰值的 **30%**。论文明确称之为「强基线」。

**结果**：8.3B + 8 路模型并行达到线性扩展的 **77%**；加上 64 路数据并行到 512 GPU 后，因为要额外通信梯度，扩展效率**略降到 74%**。

#### 5.2 Language Modeling Results Using GPT-2

三个配置：355M（等同 BERT-Large 规模，64 GPU，每 epoch 0.86 天）、2.5B（128 GPU，2.27 天）、8.3B（512 GPU，**每 epoch 约 2.1 天**）。一个 epoch 等于 68,507 步。

验证困惑度随规模单调下降，8.3B 达到 **9.27**。零样本评测见 §2.3 的表——8.3B 在 WikiText103 上取得 **10.81** 的 SOTA 困惑度，LAMBADA 上 **66.51%** 超过此前结果。

**数据污染检查**：测试集 8-gram 与训练集的重叠率——WikiText103 至多 **10.8%**，LAMBADA 至多 **1.4%**。论文补了一个重要的参照：**WikiText103 测试集与它自己的训练集本来就有 9.09% 重叠**，所以 10.8% 与前人工作一致。

论文还提到微软与 NVIDIA 合作用 Megatron 训了 17B 的 **Turing-NLG**，精度继续提升。

#### 5.3 Bi-directional Transformer Results Using BERT

这一节是全文**唯一一个与并行无关的独立贡献**，而且分量不轻。

**问题**：此前工作（ALBERT）发现把模型加大到 336M（BERT-large）以上会出现**意外的模型退化**。ALBERT 的解法是引入参数共享。

**本文的发现**：**重排 layer normalization 与残差连接的顺序**（Figure 7b，即后来通称的 pre-LN）是让 BERT 式模型突破 BERT-Large 规模的**关键**。新架构消除了原架构（post-LN）观察到的不稳定性，训练损失也更低。论文自称「据我们所知，我们是第一个报告这个改动能训练更大 BERT 模型的」。

基于此训练三个配置（每头 hidden size 固定 64）：336M（128 GPU）、1.3B（256 GPU）、3.9B（512 GPU）。336M 与 1.3B 训 200 万步，3.9B 训 150 万步**且仍在训练中**。

### 3.6 Conclusion and Future Work

复述成果：在 512 张 V100 上以 8 路模型并行训练到 83 亿参数，**整个应用维持 15.1 PetaFLOPs**；BERT 的 layernorm 位置对规模化至关重要；在 WikiText103、LAMBADA、RACE 上建立新 SOTA；代码开源。

未来方向里有一条特别值得注意：

> 训练超过 **160 亿参数**的模型所需的显存将超过一台 DGX-2H 内 16 张 GPU 的总和。对这类模型，**层内与层间模型并行的混合、外加跨节点的模型并行会更合适**。

其余方向：优化器的效率与显存占用需要改进；预训练其他模型族（XLNet、T5）；在更难更多样的下游任务上评测；用知识蒸馏训练小模型。

> **批注**：那条 160 亿参数的预测正是后来 **Megatron-LM 第二篇（张量+流水+数据 3D 并行）** 的起点，也间接催生了 ZeRO 这类优化器状态切分工作。论文很清楚地知道自己方案的天花板在哪：**张量并行被 NVLink 域的边界卡死，超出这个域就必须换维度**。这一点在 Q5 里展开。

## 4. 关键问题解析

### Q1: MLP 的两个线性层为什么一个按列切、一个按行切？如果都按同一维度切会怎样？

这是全文最核心的推导，要从**非线性算子的位置**倒着看。

MLP 是 $X \to \mathrm{GEMM}_1 \to \mathrm{GeLU} \to \mathrm{GEMM}_2 \to$ 输出。关键约束只有一条：**GeLU 是逐元素的非线性函数，要施加它，必须先拿到完整的激活值**。

**如果第一个 GEMM 按行切 $A$**（$X$ 按列切）：

$$XA = X_1A_1 + X_2A_2$$

每张卡只拿到一个**部分和**。因为 $\mathrm{GeLU}(X_1A_1+X_2A_2)\neq\mathrm{GeLU}(X_1A_1)+\mathrm{GeLU}(X_2A_2)$，必须**先 all-reduce 把部分和加起来**才能施加 GeLU。这就在 GeLU 之前插入了一个同步点。

**如果第一个 GEMM 按列切 $A=[A_1,A_2]$**：

$$[Y_1, Y_2] = [\mathrm{GeLU}(XA_1),\ \mathrm{GeLU}(XA_2)]$$

每张卡拿到的是输出的**完整的若干列**（不是部分和）。GeLU 逐元素作用，在完整的列上本地施加就是正确的。**同步点消失。**

**为什么第二个 GEMM 必须按行切**：第一个 GEMM 列切后，卡 $i$ 手里是 $Y_i$，即输出的一个列块。第二个 GEMM 算 $Z = YB$。把 $B$ 按行切成 $\begin{bmatrix}B_1\\B_2\end{bmatrix}$，则

$$Z = [Y_1, Y_2]\begin{bmatrix}B_1\\B_2\end{bmatrix} = Y_1B_1 + Y_2B_2$$

卡 $i$ 手里恰好有 $Y_i$ 与 $B_i$，可以**直接本地计算 $Y_iB_i$，不需要任何通信**——上一步的输出分布与这一步的输入需求天然咬合。代价是结果是部分和，需要在最后 all-reduce 一次。

**如果两个都按列切会怎样**：第二个 GEMM 按列切需要**完整的 $Y$** 作为输入（列切是切输出维度，输入维度不切）。而卡 $i$ 只有 $Y_i$，所以**必须先 all-gather 一次把 $Y$ 补全**。结果是通信从「一次 all-reduce」变成「一次 all-gather + 最后仍需处理」，而且中间还多了一次同步。

**如果两个都按行切**：第一个 GEMM 行切要在 GeLU 前 all-reduce（如上），第二个 GEMM 行切要求输入按列切分——恰好是 all-reduce 之后完整张量的反面。总之每层要两次通信而非一次。

**结论**：列切 → 行切这个组合，把**每层 MLP 的通信压到前向 1 次、反向 1 次 all-reduce**，是可能方案里通信最少的。原理可以概括成一句可迁移的话：

> **让第一个算子的输出分布，恰好等于第二个算子所需的输入分布；并且让非线性算子的作用范围完整落在单卡内。**

### Q2: 注意力为什么天然适合按 head 维度切分？

**因为多头注意力的 $h$ 个头在计算上完全独立**——这正是 [Multi-Head Attention](../../../concepts/multi-head-attention.md) 里那条性质的直接兑现。

回忆多头注意力的结构：$Q,K,V$ 各自经过线性投影后被切成 $h$ 份，每个头独立做 $\mathrm{softmax}(QK^\top/\sqrt{d_k})V$，最后把 $h$ 个头的输出拼接起来再过一个输出线性层。**头与头之间没有任何数据交换**，唯一的汇合点是最后的拼接。

于是切分方案几乎是被结构本身指定的：

1. **$Q,K,V$ 的 GEMM 按列切**，使得每个头的参数与计算落在单卡上。论文的原话是「使**每个注意力头对应的矩阵乘在一张 GPU 上本地完成**」。
2. 每张卡本地完成自己那几个头的完整注意力计算——**包括 softmax**。这一点是关键：softmax 在头内部跨位置耦合，但**不跨头**，所以只要一个头完整地在一张卡上，softmax 就不需要任何通信。
3. **输出线性层按行切**，直接吃下并行注意力层的输出（与 MLP 里第二个 GEMM 的道理完全相同），最后一次 all-reduce。

**与 MLP 是同一条原则的两个实例**。MLP 里非线性算子是 GeLU（逐元素，不跨任何维度耦合），所以沿输出维度切即可；注意力里非线性算子是 softmax（在头内跨位置耦合，头间独立），所以**必须沿头维度切**——这是唯一一个 softmax 不跨越的维度。

统一的判据是：**沿着非线性算子不跨越的维度切分**。

**一个重要推论：张量并行度不能超过头数。** 8 路张量并行要求至少 8 个头，且最好整除。这也解释了附录 D.1 那组数字——固定 8.3B 与 8 路并行，头数从 16 增到 32 时扩展效率从 82% 降到 77%，因为每卡分到的头变多但每个头变小，自注意力里的 GEMM 尺寸下降、softmax 元素数上升，硬件效率变差。**头数既是切分的上限，也是效率的调节旋钮。**（今天 GQA/MQA 让 KV 头数远少于 Q 头数，反而给张量并行带来了新的约束，那是 2019 年没有的问题。）

### Q3: 每个 Transformer 层前向 + 反向一共需要几次 all-reduce？分别在什么位置？

**共 4 次：前向 2 次，反向 2 次。** 论文 Figure 4 的标题写得很明确：「一个模型并行 Transformer 层的前向与反向过程中共有 4 次通信操作」。

位置如下：

| 位置 | 前向 | 反向 |
| --- | --- | --- |
| 自注意力块入口（$f$ 算子） | 恒等 | **all-reduce** |
| 自注意力块出口（$g$ 算子） | **all-reduce** | 恒等 |
| MLP 块入口（$f$ 算子） | 恒等 | **all-reduce** |
| MLP 块出口（$g$ 算子） | **all-reduce** | 恒等 |

即每个块（注意力、MLP）各贡献前向 1 次 + 反向 1 次。

**$f$ 与 $g$ 互为共轭**，这是整个实现优雅的地方：

- **$f$**：前向恒等，反向 all-reduce。放在模型并行区域的**入口**。前向时输入张量在各卡上是相同的（复制的），不需要通信；反向时各卡算出的梯度是**对同一个输入的不同部分贡献**，必须加起来。
- **$g$**：前向 all-reduce，反向恒等。放在模型并行区域的**出口**。前向时各卡持有的是部分和（因为最后一个 GEMM 行切），必须加起来；反向时梯度直接分发即可。

**为什么这个数字重要**：4 次是「每层的固定通信开销」，与并行度无关（all-reduce 的**次数**不变，单次的**数据量**才随配置变化——见 Q5）。论文能把它压到 4，靠的正是 Q1、Q2 里那两组切分把块**内部**的同步点全部消除了。作为对照，如果 MLP 与注意力各自内部还需要一次同步，每层就会变成 8 次。

**此外还有两处不在「每层」计数里的通信**：输入 embedding 之后一次 all-reduce（因为词表维度切分），以及输出层与交叉熵融合后的通信（$b\times s$ 量级，而非 $b\times s\times v$）。这两处是每次前向一次，不随层数增长。

### Q4: LayerNorm、dropout、embedding 这些部分如何处理？为什么不能像 MLP 那样切？

分三类，处理方式各不相同。

**第一类：LayerNorm、dropout、残差连接 —— 不切，复制计算。**

论文的原话：「与其让一张 GPU 计算 dropout、layer normalization 或残差连接的一部分再广播给其他 GPU，我们**选择在各 GPU 上重复这些计算**」。具体做法是每张卡维护一份**重复的 LayerNorm 参数**，模型并行区域的输出先在本地做完 dropout 与残差，再送入下一个模型并行区域。

**为什么不切？** 有两层理由：

1. **切了要付同步代价，而收益微不足道**。LayerNorm 要在 hidden 维度上做均值与方差的归约——如果 hidden 维度被切开，就需要一次跨卡归约。但 LayerNorm 的计算量相对 GEMM 小到可以忽略。**为一个廉价算子付一次昂贵的同步是明显亏本的。**
2. **论文的总体目标是「减少通信、让 GPU 保持算力受限」**。复制计算浪费的是算力（本来就有富余），换来的是通信次数不变。

一个附带好处：既然所有值要么本地、要么各卡重复，**优化器可以让每个 worker 独立更新自己那份参数，不需要通信更新后的参数值**。

**代价**：每张卡都存了一份重复的 LayerNorm 参数与**激活**。参数很小无所谓，但激活（$b\times s\times H$）在长序列下相当可观。这正是后来 **sequence parallelism** 要回收的显存——把这些复制的区域沿序列维度切开。〔这条演进论文未提及，属于后续工作〕

**第二类：embedding —— 切，但要特殊处理。**

输出 embedding 的维度是 $H\times v$，而 $v$ 达数万（GPT-2 是 50,257），**大到值得并行化**。麻烦在于输出 embedding 与输入 embedding **共享权重**，两边都得改。

- **输入 embedding**：矩阵 $E_{H\times v}$ 沿**词表维度**切 $E=[E_1,E_2]$。每个分区只有一部分词表，一个 token 的 embedding 只可能在某一张卡上非零，所以需要一次 **all-reduce（$g$ 算子）** 把结果汇总。
- **输出 embedding**：朴素做法是并行 GEMM 得到 $[Y_1,Y_2]$，再 all-gather 成完整 logits 送进交叉熵。**但 all-gather 要传 $b\times s\times v$ 个元素**——论文明确说「因词表巨大而极其昂贵」。解法是**把并行 GEMM 的输出与交叉熵损失融合**，在各卡本地算出损失，通信维度降到 $b\times s$。论文的评价：「传标量损失而不是 logits，是通信量的巨大削减」。

**为什么 embedding 能切而 LayerNorm 不能**：embedding 是一次**查表 + GEMM**，参数量巨大（$H\times v$ 可达上亿）、计算量也大，切开的收益（省显存 + 分摊计算）远超同步代价。LayerNorm 参数只有 $O(H)$、计算量微小，切开纯亏。**判据是「参数量与计算量 vs 同步代价」的比值**，不是算子的类型。

**第三类：随机数生成 —— 需要两套 RNG**（附录 B.2，一个容易忽略但必须做对的细节）。

Transformer 里的 dropout 分两处：**模型并行区域之外**（残差连接前）与**区域之内**（自注意力块里）。两者要求相反：

- 区域**外**的 dropout：各卡持有相同的张量，必须产生**相同**的 dropout 模式，否则结果不一致。做法是训练开始时用**相同的种子**初始化各 worker 的 RNG。
- 区域**内**的 dropout：各卡处理不同的分片，应该产生**不同**的随机模式，才能让整个操作真正随机。做法是**为模型并行区域内的 dropout 单独维护一个 RNG，每个 worker 用不同的种子**。

> 这一条是「复制计算」策略的隐性成本：一旦选择让多张卡算同一件事，就必须保证它们**真的算出同一个结果**，而随机性是最容易在这里出错的地方。

### Q5: 张量并行的通信量如何随并行度与 batch size 变化？为什么它通常只在单机多卡（NVLink 域）内使用？

**通信量的构成**。每层 4 次 all-reduce，每次传输的张量是 $b\times s\times H$（batch size × 序列长度 × hidden size）。所以**单次通信量正比于 $b \cdot s \cdot H$，与并行度 $p$ 无关**——这一点常被误解。

变化的是 all-reduce 本身的代价。标准 ring all-reduce 传输 $2\frac{p-1}{p}\cdot(\text{数据量})$，当 $p$ 增大时这个系数趋近 2，**增长有限**。所以：

- **随 batch size / 序列长度**：线性增长。
- **随并行度 $p$**：单次通信量基本不变，但**每卡的计算量降为 $1/p$**。

**这就是问题所在**。计算量随 $p$ 下降而通信量不变，于是**计算/通信比正比于 $1/p$ 地恶化**。附录 D.2 的强扩展实验把这个规律量得很清楚（固定 1.2B、固定 batch size 8）：

| GPU 数 | 1 | 2 | 4 | 8 |
| --- | --- | --- | --- | --- |
| 加速比 | 1.0 | **1.64** | 2.34 | **2.98** |

论文自己的解释：「2 卡快 64%。**超过 2 卡之后收益递减，因为单卡计算量下降，访存带宽与通信开销开始主导**」。8 卡只有 2.98× 而非 8×——效率仅 37%。

**为什么必须留在 NVLink 域内**：论文的硬件配置给出了直接答案——**机内 NVSwitch 300 GB/s，机间 InfiniBand 100 GB/s，差 3 倍**。而张量并行每层要通信 4 次、每次都是**阻塞的**（下一步计算必须等 all-reduce 完成，没有可以重叠的独立工作）。带宽降 3 倍、延迟又高得多，通信会直接吃掉全部收益。

对比数据并行：它每步只在**反向结束后**做一次梯度 all-reduce，且这次通信可以与反向计算**重叠**（梯度是逐层产生的，算完一层就能开始传）。所以数据并行对带宽的敏感度低得多，跨机完全可行。

**这就是三种并行的分工依据**：

| | 通信频率 | 单次通信量 | 能否重叠 | 适合的域 |
| --- | --- | --- | --- | --- |
| **张量并行** | 每层 4 次 | $b\cdot s\cdot H$ | 否（阻塞） | **机内 NVLink** |
| **流水并行** | 每个 stage 边界 1 次 | $b\cdot s\cdot H$（点对点） | 是（可与其他 microbatch 重叠） | 跨机可接受 |
| **数据并行** | 每步 1 次 | 参数量 | 是（与反向重叠） | **跨机** |

论文在结论里已经预见到了这个天花板：超过 160 亿参数就装不下一台 DGX-2H 的 16 张卡，**必须引入层内与层间模型并行的混合以及跨节点模型并行**。这正是 Megatron 第二篇论文（3D 并行）的起点。

实践中的经验法则由此而来：**张量并行度 ≤ 单机 GPU 数（通常 8），超出的规模靠流水并行跨机、再靠数据并行扩吞吐。**

### Q6: 张量并行与数据并行、流水并行的分工是什么？三者组合时的约束在哪？

**分工**（三者解决的是不同的问题）：

| 维度 | 切什么 | 解决什么 | 主要代价 |
| --- | --- | --- | --- |
| **数据并行** | 切 batch | 提高**吞吐** | 每 worker 需放下完整模型；大 batch 影响收敛 |
| **张量并行** | 切单个算子内部的矩阵 | 让**单层**装得下 | 通信频繁且阻塞，只能在高带宽域内 |
| **流水并行** | 切层 | 让**整个模型**装得下 | 流水气泡 |

论文对数据并行的批评是「模型必须完整装进一个 worker」，对流水并行的批评是「气泡，或要改优化器」，并明确说自己与流水并行「**正交且互补**」。

**混合模型+数据并行的具体组织**（附录 B.1）：

- 同一台服务器内的 2 张或更多 GPU 组成一个**模型并行组**，共同持有模型的一个实例（例如 GPU 1–8）；
- 各模型并行组中**位置相同**的 GPU 组成一个**数据并行组**（例如 GPU 1, 9, …, 505），组内所有 GPU 持有相同的模型参数；
- 反向传播时，在每个数据并行组内**并行地**跑多个梯度 all-reduce；
- 总 GPU 数 = 模型并行组数 × 数据并行组数。8.3B 的配置就是 8 路模型并行 × 64 路数据并行 = **512**。
- 所有通信通过 PyTorch 调用 NCCL 实现。

**组合时的约束**：

1. **总 GPU 数必须是各并行度的乘积**——$N = d \times t \times p$。这是硬约束，决定了集群规模不能任意取。
2. **张量并行度 $t$ ≤ 单机 GPU 数**（Q5），且 **$t$ ≤ 注意力头数**且最好整除（Q2）。论文把每头 hidden size 固定为 96/64，正是为了让切分整齐。
3. **词表要能被 $t$ 整除**，且每卡词表最好是 128 的倍数以获得高效 GEMM——论文因此把 50,257 pad 到 **51,200**（$= 128\times8\times50$）。这是一个很具体的、容易踩的坑。
4. **全局 batch size = 每卡 microbatch × 数据并行度 × 梯度累积步数**。数据并行度增大会推高全局 batch，而论文 §2.3 已指出大 batch 会损害收敛。**所以数据并行度不能无限增大——这是一个来自优化而非系统的约束。**
5. **流水并行度受层数限制**，且气泡比例正比于 $(p-1)/m$（$m$ 为 microbatch 数），要求足够多的 microbatch 来摊薄。〔这条是后续工作的结论，本文只做了定性讨论〕

**今天的经验顺序**：先用张量并行填满机内（$t=8$），再用流水并行跨机把模型装下，最后用数据并行扩吞吐；序列并行则用来回收张量并行中被复制的那部分激活显存（见 Q4）。这套顺序的依据就是 Q5 那张通信特性表。

### Q7: 这篇 2019 年的 arXiv 预印本，评测规格与今天的会议论文差在哪？

差得相当明显，值得逐条对照——这既是读这篇论文时需要的警惕，也是理解「工程报告 vs 会议论文」区别的好例子。

**1. 没有与主要竞争方案的实测对比**。§2.3 定性讨论了 GPipe、Mesh-TensorFlow、FlexFlow、PipeDream，但**实验部分一次都没有和它们比过**。论文对 GPipe 的批评是「有流水气泡」、对 Mesh-TensorFlow 的批评是「需要新语言与编译器」——**这两条都是没有数据支撑的定性断言**。一篇会议论文很难通过这一关。

**2. 扩展效率的基线选择偏乐观**。所有扩展数字都以「单卡 1.2B 配置」为基线。论文强调这是强基线（39 TFLOPS，峰值的 30%）——这点确实诚实。但**弱扩展的口径是「模型也在变大」**：8.3B 在 8 卡上达到「线性扩展的 77%」，比较的是「8 卡跑 8.3B」与「1 卡跑 1.2B × 8」。这两者的计算量构成并不完全等价（更大的模型 hidden size 更大，GEMM 效率本身更高）。**真正能反映张量并行开销的是附录 D.2 的强扩展数据——8 卡只有 2.98×（37% 效率）**，这个数字比正文的 77% 难看得多，却被放在附录。

**3. 没有通信量的解析模型**。全文没有给出「通信量 = $f(b, s, H, t)$」这样的公式，也没有计算/通信比的分析。所有结论都是实测点，无法外推到别的配置。作为对比，同期的系统会议论文通常会要求一个成本模型。

**4. 消融实验几乎没有**。「列切+行切」这个核心设计**没有与「行切+列切」或其他组合做实测对比**——论文只给了理论论证（会多一个同步点），没有量化那个同步点值多少。同样，「复制 LayerNorm」vs「切分 LayerNorm」也没有对比数据。

**5. 3.9B 的 BERT「仍在训练中」**（§5.3 原文：is still training）。用一个未训完的模型报告 SOTA，在会议论文里会被要求补完。

**6. pre-LN 的发现只有一张训练损失图**。这个发现的重要性极高（决定了 BERT 能否规模化），但证据只有 336M 与 752M 两个规模的损失曲线，**没有机制分析、没有梯度统计、没有在 GPT 侧验证**。

**7. 单一硬件平台**。全部实验在 DGX-2H + V100 上完成。结论对互联拓扑的依赖极强（Q5），但没有在其他配置（如无 NVSwitch 的机器）上验证过退化程度。

**该怎么读它**：把它当作 **NVIDIA 的一份高质量工程报告**——方案本身经过了最严苛的检验（被整个行业用了六年），但**论文提供的证据链**远不足以支撑「这是最优方案」这类结论。它证明的是「这个方案可行且高效」，没有证明「这个方案最好」。有意思的是，实践给出的答案比论文的证据更有力：**开源 + 简单 + 够用，让它赢下了那些论证更完备的竞争者。**

## 5. 可迁移的知识点

- [张量并行](../../../concepts/tensor-parallelism.md) —— 本文是这一技术的**出处**，该页的机制细节（列切/行切组合、按头切分、$f$/$g$ 共轭算子、通信特性）均来自本文。
- [Multi-Head Attention](../../../concepts/multi-head-attention.md) —— 「$h$ 个头彼此独立」这条性质是注意力块切分方案的**全部依据**，见 Q2。
- [残差连接与 Layer Normalization](../../../concepts/residual-and-layer-norm.md) —— 本文 §5.3 的 pre-LN 发现是这条线上最重要的经验结果之一；§4.2 的 $\frac{1}{\sqrt{2N}}$ 初始化缩放是同一问题的另一个解法。
- [学习率 Warmup](../../../concepts/lr-warmup.md) —— 本文 GPT-2 用 3k 步、BERT 用 10k 步 warmup，是大规模训练稳定性的标准配置。

**跨领域可迁移的四条：**

1. **切分方案应当服从非线性算子的位置**。先找出哪些算子不能在部分和上正确施加，再倒推数据该怎么分布。「沿着非线性算子不跨越的维度切」是一条通用判据。
2. **让上一步的输出分布恰好匹配下一步的输入需求**，中间的通信就消失了。这是「列切 → 行切」组合的本质，可以推广到任何算子链的切分设计。
3. **当算子的计算成本远低于同步成本时，复制比切分便宜**。LayerNorm 的处理就是这个判据的实例。代价是要小心处理随机性等隐性的一致性要求。
4. **通信频率、单次通信量、能否与计算重叠——这三项决定了一种并行方式适合放在哪一层互联上**。张量并行只能留在 NVLink 域内，数据并行可以跨机，原因全在这三项上。

## 6. 批判与开放问题

### 6.1 作者承认的局限

1. **规模天花板在 160 亿参数附近**（§6）。原文明确：超过 16B 的模型所需显存将超过一台 DGX-2H 内 16 张 GPU 的总和，届时需要「层内与层间模型并行的混合外加跨节点模型并行」。即**纯张量并行有硬上限**。
2. **优化器的效率与显存占用需要改进**（§6）。作者把它列为继续扩大规模的前提条件之一。
3. **头数越多扩展效率越低**（附录 D.1）。8.3B/8 路并行下，头数从 16 增到 32，效率从 82% 掉到 77%。原文的解释是自注意力里的 GEMM 变小、softmax 元素变多，并提醒「未来研究应当注意这个超参数，以设计出速度与精度平衡的大型 Transformer」。
4. **强扩展收益快速递减**（附录 D.2）。原文承认「超过 2 卡之后收益递减，因为单卡计算量下降，访存带宽与通信开销开始主导」——8 卡只有 2.98×。
5. **模型+数据并行的效率低于纯模型并行**（§5.1.1）。因为要额外通信梯度，从 77% 降到 74%。
6. **3.9B 的 BERT 尚未训练完成**（§5.3 原文：is still training），却已用于报告 SOTA。

### 6.2 我的质疑

1. **最能反映张量并行真实开销的数据被放在了附录**。正文反复强调的是弱扩展的 77%/74%，但那个口径下模型规模也在变大，GEMM 效率本身会提升。**真正衡量「切分一个固定模型要付多少代价」的是附录 D.2 的强扩展：8 卡 2.98×，效率仅 37%**。两个数字相差悬殊，而论文没有并置讨论。读者若只读正文，会对张量并行的通信开销形成过于乐观的印象。

2. **核心设计没有任何消融**。「第一个 GEMM 列切、第二个行切」是全文唯一的算法贡献，论文给了理论论证（否则 GeLU 前需要一个同步点），但**没有实测那个同步点值多少**。同样，「复制 LayerNorm 而非切分」也只有定性理由。一篇论文的核心设计缺乏定量支撑，意味着读者无法判断这个设计在别的配置下是否仍然最优。〔推断：论文未提供此类对比〕

3. **对竞争方案的批评全部是定性的**。§2.3 说 GPipe「有降低效率的流水气泡」、Mesh-TensorFlow「需要新语言与编译器」，实验部分**一次都没有与它们比较**。尤其是 GPipe——它与本文是同期工作、解决同一个问题、且论文自称与它「正交互补」。**既然互补，为什么不组合起来测一测？** 这个组合恰恰是一年后 Megatron 第二篇论文的内容，说明它当时是可做的。

4. **pre-LN 这个重要发现的证据链过于单薄**。§5.3 声称重排 layernorm 是让 BERT 突破 336M 的**关键**，并自称是首次报告。但证据只有 336M 与 752M 两个规模的训练损失曲线，**没有机制解释、没有梯度或激活的统计量、没有在 GPT-2 侧做对照实验**（而 GPT-2 那边训到了 8.3B，本来是现成的验证场）。一个被论文称为「critical」的发现，配这样的证据是不相称的。

5. **训练 token 比那一列的对比不完全公平**。§5.3 的表格显示 Megatron 用 1 倍 token 就超过了 RoBERTa（2 倍）和 ALBERT（3 倍）。但 Megatron 用的是自己聚合的 174GB 语料，与 RoBERTa、ALBERT 的训练数据**既不同源也不同量**。「用更少 token 达到更好效果」这个结论里，模型规模、架构改动（pre-LN）、数据质量三个因素**完全混在一起**，无法分离。论文没有讨论这一点。

6. **对互联拓扑的依赖没有被量化**。所有实验都在 NVSwitch（300 GB/s）机内 + InfiniBand（100 GB/s）机间的 DGX-2H 上完成。Q5 的分析表明张量并行的可行性**几乎完全由机内带宽决定**，但论文既没有在更弱的互联上测退化，也没有给出「多大带宽才够」的判据。这让「张量并行度该设多少」这个最实际的问题，在论文里得不到答案。〔推断：论文只在单一平台上实验〕

### 6.3 开放问题

1. **张量并行的通信能否与计算重叠？** 本文的 4 次 all-reduce 都是阻塞的，这是它被困在 NVLink 域内的根本原因。后续工作（如把 all-reduce 拆成 reduce-scatter + all-gather 并与 GEMM 分块重叠）部分回答了这个问题，但完全隐藏通信仍然做不到。
2. **被复制的激活显存能否回收？** Q4 指出 LayerNorm、dropout、残差区域的激活在每张卡上都有一份完整拷贝。sequence parallelism 后来把这些区域沿序列维度切开回收了这部分显存，代价是增加 all-gather / reduce-scatter。这个取舍的最优点在哪，与序列长度、hidden size 的关系如何，本文没有涉及。
3. **切分策略能否自动搜索？** 本文的切分是人工设计的、Transformer 专用的。FlexFlow 那类自动并行策略搜索在当时已经存在，但通用性与手工设计的效率之间一直有差距。对新架构（MoE、Mamba 等）而言这个问题重新变得重要。
4. **头数与并行度的耦合在 GQA 时代如何处理？** 本文假设 $Q,K,V$ 头数相同，按头切分很自然。今天 GQA/MQA 让 KV 头数远少于 Q 头数（甚至为 1），此时 KV 无法按头切到 8 张卡上——只能复制或改用别的切法。这是 2019 年不存在、今天很实际的约束。

### 6.4 后续可读

- **Reducing Activation Recomputation in Large Transformer Models（2022）** —— sequence parallelism 的出处，回收本文「复制计算」策略留下的激活显存。
- **ZeRO / DeepSpeed** —— 从优化器状态切分的角度解决显存问题，与张量并行正交，正好对应本文 §6 提到的「优化器显存需要改进」。
- **GPipe（NeurIPS'19）** —— 本文在 §2.3 定性批评但从未实测对比的流水并行方案。
- **On Layer Normalization in the Transformer Architecture（ICML'20）** —— 系统性地回答了本文 §5.3 只给出经验观察的 pre-LN 为何更稳定。
