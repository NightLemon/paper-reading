# Agent/RAG：从开发问题进入论文，再回到证据

这条路线服务于既定的 14 天应用开发准备。做到检索、工具调用、评测或性能排查时，选择下面对应的一节：先写清卡住的问题，读指定原文段落，做一个小实验，再用日志和失败样例解释判断。应用项目仍是主线，不额外安排必须读完的论文数量，也不要求先学完训练系统或 GPU 内核。

本页教学内容已通过独立 GPT-6 Astra 审阅，记录见同级 interview-guide 仓库的 `quality/reviews/013-career-cross-docs.json`；本次只同步审阅状态。下列追问依据具体工程约束自拟，配完整参考答；它们没有公司或真实招聘记录的出处。本页提出的实验尚未由本任务执行，读者需自行填写结果。

## 先分清三种进度

| 可以记录的状态 | 至少需要什么证据 | 不能由它直接推出什么 |
| --- | --- | --- |
| 读过指定段落 | 原文版本、章节定位、自己的机制解释、至少一个边界反例 | 看见仓库有笔记不代表自己读过；也不能推导已运行代码 |
| 跑过一个实验 | 当前代码与数据 hash、精确命令、环境、输出和失败记录 | API 返回成功、离线 fixture 通过都不能代替论文结果复现 |
| 复现某项论文结果 | 指明原文图表/结论，匹配数据、模型、训练/推理配置、基线、指标及统计方法，记录差异 | 更小硬件、不同模型或自编数据的演示只能覆盖明确说明的机制或缩小设置 |

仓库论文索引中的“笔记完成”只描述笔记文件。当前 Raft、Attention、vLLM 和 CacheRoute 已有完整笔记；Orca、FlashAttention、Megatron-LM 仍是待读骨架。RAG、ReAct、Toolformer 在本仓库尚无完整精读目录。

### 问题一：检索到了内容，为什么回答还不能交付？

**原文机制。** RAG §2 把检索到的文档作为潜变量，结合检索器概率与生成器概率。RAG-Sequence 对整段输出使用同一个文档潜变量后做边缘化；RAG-Token 在每个 token 位置做文档边缘化。这里的 RAG-Token 不意味着每生成一个 token 都向外部搜索服务重新发请求：原文先取得输入对应的 top-k 文档，再组合各文档下的生成分布。§2.4 的实现固定文档编码器与索引，微调查询编码器和 BART 生成器。

**迁移到应用的判断。** 普通应用可以先采用“固定检索 → 组装上下文 → 生成 → 核验”的流程，暂不训练检索器。先定位错误发生在哪层：候选中没有正确证据、证据过期或互相冲突、上下文被截断、模型误读，或者引用只对应了文档地址却没有支持具体结论。只看最终回答分数会把这些问题混在一起。

**一个可做的小实验（建议，尚未运行）。** 取一份有版本记录的小型资料集，人工选出“可由单条资料回答、需要两条资料、资料缺失、旧新资料冲突”四类问题，先标注允许的答案或拒答，以及支持答案的完整证据集合。保持模型、问题与输出预算上限一致，比较无检索、固定检索后生成两种流程；再对固定检索分别注入漏掉关键文档、加入旧版本、删除被引用段落三种故障。每次保存实际召回 ID、排序、被传入模型的证据版本和输出，不只保存答案。

**验收证据。** 可回答问题分别统计每题检索到的金标证据比例，以及完整证据集合是否被找齐；需要两条证据的题不能只命中其中一条就算完整召回。另查答案中的每个关键事实是否被对应版本的资料支持，包含引用 ID/URL 绑定与内容支持两项检查。无答案题的拒答结果单列，同时让全部输入留在任务结果分母中。以上是应用层诊断，不是原论文 RAG-Sequence 或 RAG-Token 的训练复现。

**面试追问：召回率提高了，正确率反而下降，怎么排查？**

**参考答：** 我先用同一批问题和原有金标确认指标口径，避免只保留成功回答。随后做配对排查：检索结果是否加入大量近似但错误的片段，关键证据在上下文中是否被挤出，版本是否混杂，模型是否把不可信资料中的指令当成任务。把“给定金标证据”的生成结果作为诊断对照：如果这时仍错，先修生成约束、证据组织或答案检查；如果只在实际检索下错，再调整检索、过滤和重排。最后用没有参与调参的固定问题复验，分别报告证据覆盖、答案支持、拒答和成本，不能仅凭 top-k 变大就宣布改进。

**进一步追问：引用 URL 能打开，而且 ID 与日期都匹配，是否足够？**

**参考答：** 这些检查证明引用指向了指定的资料记录，仍需确认资料支持回答的具体命题。比如一个景点介绍页存在，并不证明“明天 17 点闭馆”或某票价已经核实。我要把名称来源、实际有效日期、开放/价格证据和教学假设分开；缺少目标日期的证据时给出待核实或拒绝确认，不能用可达 URL 补成已证实事实。资料更新后还应重新核验受影响的答案。

### 问题二：固定 workflow 什么时候需要变成观察驱动的循环？

**原文机制。** ReAct 把任务推理与动作交错，动作从环境取得观察，后续步骤再据此修正。原文 §3.2 包含提示示例及 Standard、CoT、Act 等对照；这些特定任务上的比较不能直接当作任意业务 Agent 都更好的证据。可迁移的是“观察影响下一步”的机制和对照方法。

**迁移到应用的判断。** 若输入必定经过固定的取数和校验流程，workflow 容易观察和验收；若中间证据决定是否补充查询、换查询或修正方案，有限步循环才可能带来价值。权限、日期、预算和最终输出检查由宿主程序执行。模型说“已验证”，或工具返回一段“忽略原规则”的文字，都不能改变这些约束。

**一个可做的小实验（建议，尚未运行）。** 沿用项目已冻结的案例，不重选成功样例；给 workflow 与 agent 同一输入、同一模型、同一工具数据和预算上限。保留程序最终 gate，对一次可修复草稿比较“向下一步提供校验反馈”与“移除这条反馈”的上下文消融。加入不可修复的预算不足、工具超时、重复动作和未知工具场景，检查失败是否带原因终止。实际调用次数不必相同，但都必须报告。

**验收证据。** 每个案例需要方案、模型/数据模式、调用次数、token 计数来源、耗时、工具错误、最终 gate 结果及终止原因。保存可观察动作、参数与观察摘要即可，不要求模型披露内部隐藏推理。离线 fake 若按代码规定“看到反馈便修复”，实验只能证明反馈通道和控制流工作；真实模型的改进需要另行实测。安全消融不关闭最终 gate。

**面试追问：Agent 多试了几轮就成功，能否说它优于 workflow？**

**参考答：** 先核对成功的定义和总分母，再看资源。多轮 Agent 与单次 workflow 在相同上限下使用的实际 token、请求数和时间可能不同；我会配对报告结果匹配率、合法输出数、失败类型和实际成本，不把合法拒绝排除，也不把接口成功率当任务成功率。如果只有自编 fake 的修复案例，结论限于机制；若真实模型多轮后也有收益，还要检查是否主要来自多花预算，必要时加入相近实际预算的固定修复 workflow 对照，再评估维护成本与稳定性。

**进一步追问：模型每次都换一种措辞，怎么判断没有进展？**

**参考答：** 文本完全相同只是一种容易检测的重复。更强的判断应关注可观察状态，例如归一化后的工具名和参数、已经获取的证据集合、候选方案是否改变、违规集合是否缩小，以及剩余预算。按业务定义有意义的状态变化，才能区分必要重试和换措辞的空转。即使暂时只实现精确重复检测，也要保留硬步数和时间预算，并在报告中明确更复杂空转仍可能一直走到预算耗尽；不能把一个字符串去重规则称作通用进展证明。

### 问题三：会输出工具 JSON，和会用工具解决问题差在哪里？

**原文机制。** Toolformer §2 先用少量 API 示范采样调用，再执行调用，根据后续 token 的加权损失是否下降过滤样本，最后用含调用结果的文本微调模型。过滤时比较带调用和结果的损失，与“不调用”和“只有调用没有结果”两种对照中的较低损失。损失改善是训练数据的筛选信号，不能直接等同于业务安全或用户任务成功。

**迁移到应用的判断。** 应用侧能分层验证：JSON 是否完整、工具是否在白名单、参数是否满足 schema 和业务边界、工具结果是否真实有效、最终任务是否完成。模型选错工具或填了错误日期，即使 JSON 完全合法，也应失败。接入现成模型的结构化调用能力，可以测试这些层次；它没有重做 Toolformer 的调用采样、筛选和微调过程。

**一个可做的小实验（建议，尚未运行）。** 针对只读的地点、天气、方案检查工具，手工构造“正确工具与参数、未知工具、合法 JSON 但错误日期、缺字段、重复调用、结果包含伪造指令”六类动作。先用离线适配器测试宿主的校验与终止，再在已有授权和明确费用预算下选少量相同业务问题做真实模型测试。不要把原始密钥或认证头放入日志。

**验收证据。** 分别列出 schema 通过数、业务参数通过数、有效工具结果数、最终合法输出数及错误分类；这些数不能互相替代。若要声称复现 Toolformer，还必须另外给出训练数据生成、损失过滤、训练配置与对应评测的证据。本路线不要求在 14 天应用主线里完成这套训练。

**面试追问：为什么还要在模型之外重复校验？模型不是已经按 schema 调用了工具吗？**

**参考答：** Schema 约束表达形状和部分取值，业务约束通常还依赖真实状态。日期字符串合法不表示天气服务覆盖该日期，票价字段为数字不表示价格来自可信资料，总价也可能漏掉人数或住宿。宿主要把已验证的请求、可信数据版本与结果绑定，重新计算关键约束，并在发布最终结果前执行检查。工具输出本身是外部数据，不能赋予新权限；模型的文字承诺也不能代替这些检查。

## 有实际瓶颈时，再回到已有系统笔记

这部分属于按需深入。先完成一个可解释、可测试的应用流程，再选择自己确实遇到的问题。

| 触发问题 | 可读的已有资料 | 小实验与需要保留的证据 |
| --- | --- | --- |
| 相似请求成本高，但不知道是否用了 prefix cache | [KV Cache](concepts/kv-cache.md)、[Prefix Caching](concepts/prefix-caching.md)、[CacheRoute §4–6](topics/llm-serving/2026-cacheroute/README.md) | 固定模型、请求内容、顺序与路由条件，观察静态前缀和动态检索片段改变时的实际 usage/延迟；缓存字段缺失时记录未知，不推断固定 TTL |
| 计划扩容，却没有定位等待发生在哪里 | [vLLM §2–4](topics/llm-serving/2023-vllm-pagedattention/README.md)、[SLO 容量](concepts/slo-capacity.md) | 先拆分客户端等待、工具 I/O 和模型请求时间；有条件再测队列、prefill/decode 与负载。论文中的硬件吞吐倍数不搬成当前 API 的收益承诺 |
| 多个 worker 会修改同一业务记录 | [Raft §4 的安全性问答](topics/distributed-systems/2014-raft/README.md)、[共识与复制状态机](concepts/consensus-and-replication.md) | 先写状态不变量和并发/重试反例，用现有事务或幂等约束验证；只有需要跨故障节点维护一致状态时，再研究共识实现 |

**面试追问：把共享提示放前面，为什么还不能保证缓存命中？**

**参考答：** 我先确认共享的是实际序列化后的相同 token 前缀，而不是语义相似的文字。模型、模板、消息顺序或前缀中的动态字段变化，都可能破坏复用条件；即使前缀相同，也还受服务端路由、缓存驻留和资源竞争影响。CacheRoute 讨论的正是局部性与负载的取舍，它不能证明任意提供方的缓存生命周期。我会保留配对请求与实际 usage 证据，观察命中和延迟的关系；提供方未公开的 TTL、cache key 和驱逐策略保持未知。

**面试追问：一个可重试的 Agent，需要自己实现 Raft 吗？**

**参考答：** 先看它管理什么状态和故障模型。本地单进程只读规划，重点是输入约束、预算、工具错误和最终 gate；引入共识没有直接解决这些问题。若多个进程会提交相同业务动作，应先使用已有数据库事务、唯一键、请求幂等键和可恢复状态机。Raft 为复制状态机提供一致日志，本身并不让外部业务副作用自动实现恰好一次；仍需处理重复请求、提交与外部动作之间的边界。只有明确需要跨节点容错且现有基础设施无法满足时，才讨论选择或实现共识组件。

### 一份足够追问的证据记录

每次练习先写问题与预期，再运行。记录至少包含：问题 ID、原文与章节、代码/数据 hash、fixture 或 live、模型与预算、精确命令、完整分母、预期业务判据、实际结果、失败原因及结论范围。没有执行时明确写“未运行”，不要填一个示意 PASS。
